# 여우굴 예약 기능 검증 결과

2026년 10월 17일, 일·월·화 저녁 **90분** 일정, 접수 불가 날짜의 **마감** 표시, 접수 후 돌아가기, 공통 메뉴와 일정 로딩 화면을 검증했습니다. 로컬 자동 검증 **42개**, Chromium 예약 브라우저 시나리오 **15개**, 시간 경계 브라우저 시나리오 **5개**, 공통 메뉴 브라우저 시나리오 **10개**, 일정 로딩 브라우저 시나리오 **6개**가 모두 통과했습니다. 실제 `Code.gs`를 Google 서비스의 메모리 대역으로 실행하며 실제 고객 예약이나 메일은 만들지 않습니다. 실제 Google 웹 앱의 새 일정 적용은 사용자의 코드 교체·새 버전 배포 후 확인해야 합니다.

기존 버전은 로컬 예약 화면을 실제 Google 웹 앱에 연결하여 접수 성공, 같은 신청 재전송 시 동일 접수번호 반환, 신청한 일정의 마감 반영을 확인했습니다. 사용자가 **Gmail 메일 1통, 시트 신청 1행, 메일 상태 발송 완료**를 모두 확인하여 테스트 수신자 기준의 실제 연동 검증을 마쳤습니다. 이후 사용자가 새 버전 배포와 매일 19시 일정 활성화 후 정상 동작을 확인했습니다. 실제 메일함의 굵은 표시 여부는 별도 확인이 필요합니다.

## 일정 조회 중 로딩 표시

- 첫 접속, 월 변경, 일정 새로 확인 시 달력 중앙에 ‘예약 일정을 불러오는 중입니다’와 회전 표시가 나옵니다. 페이지 스크립트가 늦게 로드되어도 HTML에 안내가 먼저 표시됩니다.
- 조회 중에는 날짜 상태와 이전 시간 선택지를 숨기고 날짜 선택·월 이동·신청·중복 새로고침을 막습니다. 화면 복귀 이벤트가 겹쳐도 같은 조회를 중복 실행하지 않습니다. 이름·연락처 입력과 카카오톡 문의는 사용할 수 있습니다.
- 최신 응답이 도착한 뒤에만 ‘신청 가능/마감’을 표시합니다. 브라우저 일정 캐시는 추가하지 않았습니다. 선택했던 시간이 마감되었다면 선택을 해제하고 안내하며 입력한 개인정보는 유지합니다.
- 조회 실패는 ‘마감’으로 표시하지 않고 재시도 안내로 바꿉니다. 정상적인 빈 일정 응답과 통신 오류를 구분하며, 기존 Google 요청의 45초 시간 제한이 지나면 회전 표시를 종료합니다.
- 응답 지연·서버 오류·시간 초과·재시도·월 변경을 브라우저에서 재현했습니다. 390px 모바일에서 가로 넘침이 없고, 움직임 줄이기 설정에서는 회전 애니메이션을 중지합니다. 접수 재확인과 중복 신청 방지 등 기존 예약 시나리오도 통과했습니다.
- 홈페이지만 바뀌며 Apps Script 코드·배포·수신자 설정은 변경할 필요가 없습니다.

## 접수 후 돌아가기와 카카오톡 버튼 수정

- 접수 완료 화면의 카카오톡 문의 아래에 ‘예약 화면으로 돌아가기’를 추가했습니다. 새 예약 화면을 열며 기존 신청과 마감 상태를 유지합니다. PC·모바일에서 날짜·시간 재선택, 신청 행 보존, 추가 POST·메일 없음, 버튼 배치를 확인했습니다.
- 돌아간 뒤 다른 시간에 신청하면 별도 접수번호를 받습니다. 19:00 신청 후 돌아가 20:30에 신청하고, 다시 돌아가 다음 달을 조회하는 흐름도 검증했습니다.
- 카카오톡 아이콘은 HTML과 페이지 모듈이 서로 다른 URL로 `common.js`를 두 번 실행하여 한 번의 클릭에 열기·닫기가 연이어 발생했습니다. 예약·문의·예약 조회·관리자 페이지는 공통 UI를 페이지 모듈에서 한 번만 불러오도록 수정했습니다.
- 홈과 위 네 페이지를 1440px·390px에서 확인했습니다. 카카오톡 패널이 있는 페이지의 클릭·키보드 열기, 재클릭·Escape·바깥 클릭 닫기, 상담 링크 주소를 검증했습니다. 모바일 메뉴도 한 번의 클릭으로 열리고 닫힙니다. 공통 모듈은 한 번만 로드되고 JavaScript 예외는 없습니다.
- 이 수정은 홈페이지 코드만 바뀌므로 Apps Script 수정·새 버전 배포는 필요하지 않습니다.

## 운영 알림 수신자 두 곳 추가

- 운영 모드의 새 신청은 `replate.kr@gmail.com,foxcavebrew@naver.com`을 함께 수신자로 지정하며 한 신청의 재전송으로 메일을 중복 발송하지 않습니다.
- 수신자 2명분의 잔여 한도가 없으면 신청은 저장하고 메일만 대기합니다. 한도 복구 후 두 주소로 한 번 발송하는 동작을 검증했습니다.
- 이전에 저장한 단일 수신자 신청은 재시도할 때 원래 수신자를 유지합니다. 알 수 없거나 중복된 수신 주소는 발송하지 않습니다.
- 테스트 모드와 `sendTestEmail`은 리플레잇 주소만 사용합니다.
- `useProductionRecipientTest` 실행 후 정식 도메인에서 접수하면 실제 서버 저장 경로를 거쳐 리플레잇 단독 수신으로 처리합니다. 같은 환경에서 `useProductionRecipient`를 실행한 뒤 두 주소 수신으로 바뀌고 다시 테스트 모드로 돌아오는 동작을 검증했습니다. 설정 함수 실행만으로 메일이 발송되거나 기존 신청·일정이 초기화되지 않습니다.
- 사용자가 최신 Apps Script 배포와 테스트를 마쳤으며 `useProductionRecipientTest`를 실행해 두었다고 확인했습니다. 배포 전 Google health 조회도 `mode=TEST`입니다. **실제 두 수신함 도착은 운영 모드 전환 후 별도 확인이 필요합니다.**

## 일·월·화 90분 일정과 마감 표시 검증

- 2026-10-19부터 종료일 없이 일·월·화에 19:00, 19:30, 20:00, 20:30을 생성합니다. 10월은 5일 × 4개 = 20개이며 다음 달과 윤년·비윤년도 검증했습니다. 자동 일정 행을 시트에 쌓지 않습니다.
- 19:00 예약 뒤에는 20:30, 20:30 예약 뒤에는 19:00만 남습니다. 19:30 또는 20:00 예약 뒤에는 네 시간이 모두 닫힙니다.
- 19:00과 20:30은 어느 순서로도 함께 예약할 수 있습니다. 두 팀이 접수되면 하루 전체가 마감되고, 한 팀만 취소하면 다른 팀과 겹치지 않는 시간만 다시 열립니다.
- 각 접수는 90분으로 저장하고 화면의 선택 시간·완료 내역에 종료 시간까지 표시합니다. 마지막 수업은 22:00에 끝납니다.
- 지난 날짜, 휴무일, 시작 시간이 지난 날짜, 직접 닫은 날짜와 예약으로 찬 날짜는 모두 달력에 ‘마감’으로 표시합니다. 가능한 시간이 하나라도 남으면 ‘신청 가능’입니다.
- 한국과 날짜가 다른 미국 시간대 브라우저에서도 한국 날짜·월을 표시합니다. 페이지를 연 상태에서 시작 시간이 되면 새 신청을 막고 선택을 해제합니다. 이 화면 갱신 자체는 Google 요청을 추가하지 않습니다.
- 저장 응답이 불확실한 기존 신청은 시작 시간이 지나도 같은 접수번호로 재확인할 수 있습니다.
- 일정 활성화·중지·재설정은 수신자 모드, 기존 예약과 수동 일정을 유지합니다. 이전 활성화 설정과 `enableDailyEveningSchedule` 함수 이름도 새 주간 일정으로 이어집니다.
- 예전 60분 예약은 저장된 길이를 그대로 유지합니다. 운영자가 D열 소요시간을 명시적으로 90분으로 바꾸면 늘어난 구간의 예약을 막습니다.
- 같은 날짜·시작 시간의 수동 행이 자동 일정보다 우선하며 네 시간을 모두 닫아야 하루가 마감됩니다. 수동 행을 삭제하면 해당 자동 일정이 복원됩니다.
- HTML 알림 메일의 굵은 항목명, 입력 이스케이프, 두 수신자·TEST 모드 전환, 중복 발송 방지와 재시도 검증도 통과했습니다.
- 데스크톱 1440px와 모바일 390px에서 네 시간 선택, 종료 시간과 마감 표시를 확인했습니다. 가로 넘침과 JavaScript 예외가 없습니다.

실제 Google 적용 순서는 [설치 가이드의 ‘일·월·화 90분 일정 적용’ 절](google-apps-script-setup.md#이미-설치했다면-일월화-90분-일정-적용)에 있습니다. 기존 60분 수동 행과 테스트 행이 새 자동 일정을 덮어쓰지 않도록 가이드의 시트 정리 기준을 확인해야 합니다.

## 검증 실행 방법

Node.js 20 이상에서 프로젝트 폴더를 열고 실행합니다. npm 패키지 설치는 필요 없습니다.

```sh
npm test
```

브라우저 검증은 터미널 하나에서 로컬 테스트 서버를 실행한 뒤, 다른 터미널에서 Playwright CLI로 실행합니다. Playwright CLI 자체는 설치되어 있어야 합니다.

```sh
npm run test:serve
```

```sh
mkdir -p output/playwright
playwright-cli -s=foxcave-booking open http://127.0.0.1:4173/booking/
playwright-cli -s=foxcave-booking run-code --filename tests/browser-checks.js
playwright-cli -s=foxcave-booking run-code --filename tests/booking-time-browser-checks.js
playwright-cli -s=foxcave-booking run-code --filename tests/navigation-browser-checks.js
playwright-cli -s=foxcave-booking run-code --filename tests/booking-loading-browser-checks.js
playwright-cli -s=foxcave-booking close
```

Codex의 Playwright 스킬 환경에서는 `playwright-cli` 대신 `~/.codex/skills/playwright/scripts/playwright_cli.sh`를 사용할 수 있습니다.

검증을 마치면 테스트 서버를 실행한 터미널에서도 `Ctrl+C`로 종료합니다.

`tests/booking-server.mjs`는 4173번에서 홈페이지, 4174번에서 Google 응답을 대신하는 서비스를 실행합니다. 실제 `apps-script/Code.gs`를 평가하지만 시트와 메일은 메모리에만 남깁니다. **이 테스트 서버를 운영 배포하지 않습니다.** 캡처는 `output/playwright/`에 저장되며 Git에 포함하지 않습니다.

| 실제 Google 출처의 CORS 및 리다이렉트 | 로컬 홈페이지에서 GET 및 text/plain POST 성공, script.googleusercontent.com의 JSON 응답을 브라우저에서 읽음 |
| 실제 서버 입력 검증 | 동의하지 않은 POST를 CONSENT 오류로 거절, 예약이나 메일을 생성하지 않는 점검 |
| iOS Safari 및 카카오톡 내장 브라우저 | 별도 실기기 확인 필요 |

[설치 가이드](google-apps-script-setup.md)의 4~7단계로 실제 서비스 검증을 진행합니다. `site/booking-config.json`에는 전달받은 배포 URL을 연결했습니다. 이 기록은 새 일정 배포 전 점검 결과를 포함하며 Google 설정은 변경하지 않았습니다. 홈페이지는 `main`에 push하면 GitHub Pages가 배포합니다. 실제 반영 여부는 [GitHub Actions 배포 기록](https://github.com/znwxyz/foxcave/actions)과 공개 예약 화면에서 확인합니다.
