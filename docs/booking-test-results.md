# 여우굴 예약 기능 검증 결과

2026년 10월 17일 배포 전, 원격 `main`의 최신 커밋 `e84b6f6`을 합친 상태에서 로컬 검증 **39개**와 Chromium 브라우저 시나리오 **10개**를 다시 실행해 모두 통과했습니다. 원격의 제품 정보·FAQ·기업 강의 변경을 유지했고, 예약 페이지에서 겹친 스타일·스크립트 참조를 새 예약 기능과 함께 반영했습니다. 로컬 시나리오는 Google 서비스를 메모리 대역으로 실행하며 실제 메일을 보내지 않습니다.

기존 버전은 로컬 예약 화면을 실제 Google 웹 앱에 연결하여 접수 성공, 같은 신청 재전송 시 동일 접수번호 반환, 신청한 일정의 마감 반영을 확인했습니다. 사용자가 **Gmail 메일 1통, 시트 신청 1행, 메일 상태 발송 완료**를 모두 확인하여 테스트 수신자 기준의 실제 연동 검증을 마쳤습니다. 이후 사용자가 새 버전 배포와 매일 19시 일정 활성화 후 정상 동작을 확인했습니다. 실제 메일함의 굵은 표시 여부는 별도 확인이 필요합니다.

## 운영 알림 수신자 두 곳 추가

- 운영 모드의 새 신청은 `replate.kr@gmail.com,foxcavebrew@naver.com`을 함께 수신자로 지정하며 한 신청의 재전송으로 메일을 중복 발송하지 않습니다.
- 수신자 2명분의 잔여 한도가 없으면 신청은 저장하고 메일만 대기합니다. 한도 복구 후 두 주소로 한 번 발송하는 동작을 검증했습니다.
- 이전에 저장한 단일 수신자 신청은 재시도할 때 원래 수신자를 유지합니다. 알 수 없거나 중복된 수신 주소는 발송하지 않습니다.
- 테스트 모드와 `sendTestEmail`은 리플레잇 주소만 사용합니다.
- `useProductionRecipientTest` 실행 후 정식 도메인에서 접수하면 실제 서버 저장 경로를 거쳐 리플레잇 단독 수신으로 처리합니다. 같은 환경에서 `useProductionRecipient`를 실행한 뒤 두 주소 수신으로 바뀌고 다시 테스트 모드로 돌아오는 동작을 검증했습니다. 설정 함수 실행만으로 메일이 발송되거나 기존 신청·일정이 초기화되지 않습니다.
- 사용자가 최신 Apps Script 배포와 테스트를 마쳤으며 `useProductionRecipientTest`를 실행해 두었다고 확인했습니다. 배포 전 Google health 조회도 `mode=TEST`입니다. **실제 두 수신함 도착은 운영 모드 전환 후 별도 확인이 필요합니다.**

## 매일 19시 일정과 메일 서식 추가 검증

- 2026-10-19~31의 13개 일정, 이후 달 전체, 2027년 2월 28일·2028년 2월 29일·2100년 2월 28일을 정확히 생성합니다. 종료일은 없으며 시트에 자동 일정 행을 쌓지 않습니다.
- 일정 활성화·중지·재설정은 기존 예약, 수동 일정과 수신자 모드를 유지합니다.
- 수업 일정 시트에 같은 날짜·19:00 행을 넣으면 휴무·최대 인원·시간 길이 설정이 자동 일정보다 우선합니다.
- 19:00~20:00 예약과 19:30~21:00 예약은 겹치므로 하나만 접수됩니다. 18:00~19:00 또는 20:00~21:00처럼 경계만 맞닿는 수업은 허용합니다. 날짜·월을 넘기는 겹침도 거절합니다.
- 신청한 화면에서는 저장 성공 직후 해당 시간대를 마감 표시합니다. 새로 연 페이지에서도 마감으로 표시되고, 다음 달 전체 자동 일정도 조회됩니다.
- HTML 메일의 항목명은 굵게 표시하고 고객 입력의 HTML 문자를 이스케이프합니다. 요청사항의 줄바꿈과 일반 텍스트 본문도 유지합니다.
- `sendTestEmail`은 새 예약 메일과 같은 서식의 가상 예시를 테스트 수신자에게만 보내며 신청 행을 만들거나 시간을 마감하지 않습니다.

실제 Google 적용 순서는 [설치 가이드의 ‘이미 설치했다면’ 절](google-apps-script-setup.md#이미-설치했다면-굵은-메일-항목명과-매일-19시-일정-적용)에 있습니다. 예전 10월 20일 19:30 테스트 신청이 살아 있으면 새 19시 일정도 겹침으로 마감되므로 테스트 신청은 취소하고 테스트 일정은 닫아야 합니다.

## 검증 실행 방법

Node.js 20 이상에서 프로젝트 폴더를 열고 실행합니다. npm 패키지 설치는 필요 없습니다.

```sh
npm test
```

브라우저 검증은 터미널 하나에서 로컬 테스트 서버를 실행한 뒤, 다른 터미널에서 Playwright CLI로 실행합니다. Playwright CLI 자체는 설치되어 있어야 합니다.

```sh
npm run test:serve
```

```sh
mkdir -p output/playwright
playwright-cli -s=foxcave-booking open http://127.0.0.1:4173/booking/
playwright-cli -s=foxcave-booking run-code --filename tests/browser-checks.js
```

Codex의 Playwright 스킬 환경에서는 `playwright-cli` 대신 `~/.codex/skills/playwright/scripts/playwright_cli.sh`를 사용할 수 있습니다.

`tests/booking-server.mjs`는 4173번에서 홈페이지, 4174번에서 Google 응답을 대신하는 서비스를 실행합니다. 실제 `apps-script/Code.gs`를 평가하지만 시트와 메일은 메모리에만 남깁니다. **이 테스트 서버를 운영 배포하지 않습니다.** 캡처는 `output/playwright/`에 저장되며 Git에 포함하지 않습니다.

Apps Script 코드와 발송 모드는 홈페이지 배포로 변경되지 않습니다.
